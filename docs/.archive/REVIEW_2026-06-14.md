## 三、為什麼 ignored_keywords 失效？

### 設計面

`config.yaml` 定義了 6 個應該被無視的關鍵字：

```yaml
ignored_keywords:
  - "我要訂購"
  - "菜單"
  - "常見問題"
  - "黑羽放山雞介紹"
  - "蔥鹽醬介紹"
  - "吃法介紹"
```

這些是 LINE 官方帳號的 **Rich Menu / 圖文選單 / 關鍵字回應** 自動產出的客戶訊息（不應由 AI 回覆，因為 LINE 已經回覆了圖文訊息）。

### 程式碼面

`src/config.js` 的 `isIgnoredKeyword()` 邏輯正確（100% 完全比對），但**從未被 production 呼叫**。

`src/index.js` 有兩處呼叫 `isIgnoredKeyword()`：
- `handleWebhookEvent` 第 122 行
- `handleMessage` 第 56 行

但這兩個函數**都沒有被 production 環境使用**。

### 真正的關卡

| 層次 | 機制 | 是否過濾 ignored_keywords |
|------|------|--------------------------|
| Cloudflare Worker | `BLOCKED_PATTERNS` (Prompt/SQL injection) | ❌ |
| Cloudflare Worker | `PAYMENT_KEYWORDS` (短訊息 ≤50 字) | ❌ |
| OpenClaw external-user agent | LLM 自主判斷 | ❌（無 prompt 指令） |

**結果**：客戶輸入「菜單」時，訊息直接送進 LLM，LLM 看到「菜單」就嘗試回答，導致重複回覆（LINE 圖文選單已經回覆過了）。

## 五、修補計畫（分階段）

### Phase A：修復 Bug（讓 production 真正過濾 ignored_keywords）

**目標**：讓客戶輸入「菜單」時，Bot 真的不回覆（讓 LINE 自己的圖文選單負責回覆）。

**選項 A1：在 Cloudflare Worker 加攔截**（建議）
- 優點：早一步阻擋，省 LLM 成本
- 缺點：Worker 程式碼也要維護，要部署
- 實作：在 `cloudflare-worker/src/index.ts` 加 `IGNORED_KEYWORDS` 陣列，類似 `PAYMENT_KEYWORDS` 的攔截邏輯

**選項 A2：在 OpenClaw external-user agent 的 prompt 加指令**
- 優點：不用部署 Worker
- 缺點：要 LLM 自己判斷「這 6 個關鍵字要沉默」，浪費 token，且不 100% 可靠
- 實作：在 `~/.openclaw/agents/external-user/AGENTS.md` 或 `knowledge/main_idea.md` 加「若客戶輸入完全符合以下 6 個關鍵字，直接回覆 '🐔' 或留空回覆」

**選項 A3：兩者都做**（最安全）
- Worker 過濾為主（100% 可靠）
- Agent prompt 也加指令（多層防護）

**建議**：選項 A1（Worker 層攔截，乾淨俐落）

**問題**：雞肉專案的 `src/` 沒有被 production 執行，這有兩條路：

**選項 D1：保持現狀（設計文件 + 測試對象）**

- Production 用 OpenClaw external-user agent
- 不再要求兩邊邏輯同步

**選項 D2：將雞肉專案改造成可被 OpenClaw 引入的 Skill**
- 將 `src/index.js` 暴露為 OpenClaw 工具函數
- 讓 external-user agent 在 LLM 判斷後調用 `handleMessage` 等函數
- 優點：可以保留結構化邏輯（rules 驗證、state machine 等）
- 缺點：需要改造 OpenClaw 整合機制

**選項 D3：將雞肉專案獨立部署為 Cloudflare Worker**
- 雞肉專案改寫成 Cloudflare Worker
- 完全取代 OpenClaw external-user agent
- 優點：邏輯完全可控
- 缺點：失去 OpenClaw 框架優勢（記憶、知識庫載入等）

**建議**：先保持 D1，Phase A 修完後再評估 D2/D3 的成本效益。
